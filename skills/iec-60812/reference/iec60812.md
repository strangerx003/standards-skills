# IEC 60812:2006 — FMEA/FMECA — Full Reference

Source: IEC 60812, 2nd edition 2006-01 (IEC TC 56 Dependability). Bilingual EN/FR. Superseded technically in 2018 by the 3rd edition which formalizes functional FMEA and interface analysis; the 2006 details below are from the actual document held.

## 1. Scope & framework
- Describes FMEA and FMECA, guidance for applying them: procedural steps, terms, assumptions, criticality measures, failure modes, basic principles, example worksheets.
- Normative: IEC 60300-3-1:2003; relates to IEC 61025 (FTA), IEC 61078 (RBD), IEC 61165 (Markov).
- Definitions (Cl. 3): item; failure = termination of ability to perform required function (IEV 191-04-01); "fault" used interchangeably for historical reasons; failure effect 3.4; failure mode 3.5; failure criticality 3.6 (severity × frequency or other attributes = a measure of need for addressing); system 3.7; failure severity 3.8. A process can also be an item; hardware FMEA normally excludes people, process FMEA includes human actions.
- Purpose (4.2): identify failures with unwanted effects on operation/safety; improve reliability/safety/maintainability; satisfy contracts; support maintenance plans (IEC 60300-3-11).

## 2. Types & levels
- **Design FMEA** vs **Process FMEA (PFMEA)** (7.1): PFMEA on a manufacturing or work process; always starts from the **process end goal**; requires a–e (clear goal, individual steps, potential flaws per step, effect of each flaw on product, potential causes).
- **Levels** (5.2.2.3): highest level set by design concept/output requirements; lowest level where functional information available; maintenance/repair level as guide; less depth for mature designs.
- **Hardware vs functional** (5.2.2.2/5.2.3): functional study boundary allowed; failure modes derived from **design intent and detailed functional analysis** (preferred over similarity).
- **Interfaces** (5.2.2.4–6): boundary = physical & functional interfaces with environment and interacting systems; inputs/outputs, redundancy, alternative signal paths, operator/system interfaces captured; out-of-boundary items explicitly excluded.
- **Hierarchy propagation** (Fig. 1): local failures propagate up — a part's failure-mode *effect* becomes the *failure mode* and *cause* of the next level.

## 3. Procedure (5.1–5.2)
Four stages (5.1): plan (ground rules, scheduling, expertise) → execute → summarize/report → update as development progresses. Reuse acceptable only under same use/stresses.

**Planning (5.2.1)**: in dependability program plan; scope by design maturity/critical functions/new tech; worksheet revision control & archiving; milestones; action closure. Project-management approval.

**Structure/system (5.2.2)**: elements/characteristics, logical connections, redundancy level & nature, position, I/O, structural change between operating modes; features for initiation/operation/control/maintenance — durations of functions, intervals between periodic tests, time available for corrective action, facility/personnel interfaces, start-up/shutdown, control, preventive/corrective maintenance, routine test procedures; environment conditions & assumptions updated as data improves.

**Failure mode determination (5.2.3)** + consult suppliers; sources: similar items/test data; design intent + detailed functional analysis (preferred); in-service records/failure data; inference from functional/physical parameters. Generic modes (Table 1): failure during operation; failure to operate at prescribed time; failure to cease operation at a prescribed time; premature operation. Record estimate status; **mitigation is more important than the exact probability**.

**Causes (5.2.4)**: most likely independent causes per mode; depth proportional to severity of effects; from field/test or judgment; recommended actions evaluated by probability × severity.

**Effects (5.2.5)**: operation/function/status consequences; **local** effect = on the item itself (basis for corrective action; may be none beyond the mode); **system/end effects** = impact on the highest level, through all intermediate levels, may arise from **multiple failures** (e.g. safety device fails AND exceeds limits) — must be flagged.

**Detection (5.2.6)**: built-in test, pre-operation checkout, inspection during maintenance; at start-up, continuous or interval; detection/annunciation should preclude hazardous conditions; list other modes with identical manifestations; design FMEA: design deficiency detection means (review/analysis/simulation/test); process FMEA: probability catch by controls (operator, SPC, quality check, later steps).

**Compensating provisions (5.2.7)**: redundant items, alternative means, monitoring/alarm, damage-limiting; update analysis when elements reconfigured.

**Severity classification (5.2.8, Table 2 example)**: IV Catastrophic (primary-function failure with serious damage and/or personal injury) / III Critical (considerable damage, no serious life-injury threat) / II Marginal (degradation, no damage/injury) / I Insignificant (degradation only). Depends on application; contractual and government/industry safety requirements relevant.

**Frequency/probability (5.2.9)**: account for operational profile (stress-dependent rates); sources: life tests, failure-rate databases, field/similar-item data; **the analysis must state the time period** (warranty or predetermined life).

**Flowchart (5.2.10, Fig. 2)**: initiate → select component → identify modes → pick mode → immediate+final effect → severity → causes → occurrence estimate over stated period → decide if severity/probability warrants action → propose mitigation/compensation with owners → record → loop → close with revision date.

## 4. FMECA / risk (5.3)
- Criticality analysis purpose (5.3.1): SET priorities for mitigation; criticality + severity define priority.
- **RPN (5.3.2)**: R = S×P, with optional **D** (detection, inverted rank). RPN = S×O×D. If P < 0.2, criticality number C (5.3.4) may substitute. Where no measures available, use **non-numeric FMEA**. Similar/identical RPN → higher severity mode first. Scale choices: 1–4/5, or automotive 1–10 (S/O/D).
- **FMECA vs risk analysis (5.3.3)**: criticality+severity is a risk measure but relative; for high-risk/high-complexity systems **FMECA must not be the sole basis for judging risk acceptability** — do PRA (exposure time, avoidance probability, latency, detection). Two criticality approaches: criticality matrix and RPN. Criticality matrix: severity I–IV vs likelihood classes E→A; defined by the analyst, approved by programme/management; example scale (E Improbable 0≤Pi<0.001; D Remote <0.01; C Occasional <0.1; B Probable <0.2; A Frequent ≥0.2); same-indenture-level comparison only; in some applications severity has absolute priority over frequency.
- **Criticality number (5.3.4)**: λi = αi·λj·βi; **C ≈ λi·tj**; **Ci ≈ λi·tj** (probability P ≈ 1−e^−C ≈ C for small C); sum λi·tj per component; note "criticality number" is a risk measure not a probability; with variable failure rate, use probability.
- **Criticality matrix (5.3.4.1, Fig. 3)**: severity × likelihood; **no universal definition of criticality** — analyst sets it and management approves; **only failure modes at the same indenture level** are meaningfully compared; in some applications severity has absolute priority.
- **Risk acceptability (5.3.5, Table 3)**: matrix per severity (Insignificant→Catastrophic) × frequency (Improbable→Frequent) grouped into Negligible/Tolerable/Undesirable/Intolerable; explicitly subjective/industry-dependent.
- **Automotive scales (5.3.6)**: Severity (Table 4, SAE J1739): 1 none; 2–4 cosmetic/squeak-rattle; 5–7 comfort/operability; 8 item inoperable; 9 hazardous **with** warning; 10 hazardous **without** warning (safe-vehicle operation or regulation non-compliance). Occurrence (Table 5, AIAG 3rd): 1≤0.010 per 1 000 items (≤1×10⁻⁵) … 10 ≥100/1 000 (≥1×10⁻¹); frequency = fraction failed over the designated period — must be stated. **Scale neither linear nor logarithmic → RPN non-linear; special care.** Detection (Table 6, AIAG): 1 almost certain detection by design control … 10 absolutely uncertain; process FMEA definition = probability the current process controls catch before next process/customer. For generic product across systems, D hard to estimate.
- **RPN deficiencies (5.3.6.4) — verbatim-quality cautions**: ~88% of range unused; duplicates across factor combinations; sensitivity distortion (same increment matters more when other factors large); inadequate scaling (occurrence ratios 2–2.5×, not 10×); non-linear (S6/O4/D2 = 48 vs S6/O5/D2 = 60); ordinal scales → misleading conclusions from direct RPN comparison. Example S10/O3/D2 (RPN 60) deserves action before an S5/O5/D5 "average" (RPN 125); **high severity 9–10 has priority regardless of RPN**; mitigation focus on severity first, review S/O/D individually. "Review of an RPN requires caution and good judgment."
- **APN** in process FMECA (Annex B.3) = essentially RPN for process.

## 5. Considerations (Cl. 6)
- **CCF (6.1)**: defeats independence — sources: design (software, rating), manufacturing (batch flaws), environment (EMI, temperature cycling, vibration), human error (maintenance/operation); consider CCF for redundant systems; FMEA alone insufficient → combine with functional diversity, physical separation, testing; preventive measures in Remarks.
- **Human factors (6.2)**: partial error-mode lists still reveal deficiencies; complete enumeration impossible; interlocks/passwords count as mitigation; many CCFs involve human error.
- **Software (6.3)**: HW–SW interrelationships must be identified; post-design software changes may invalidate FMEA; software-error effects postulated only to a limited extent; fallback provisions (sw or hw) emerge from the analysis.
- **Consequential categories (6.4)**: fail-safe, repairable, non-repairable, degraded mission, mission failed, individuals/groups/society; link to ultimate consequence via FTAs, Markov graphs, Petri nets.

## 6. FMEA ↔ FTA (7.4, 7.3, 4.1)
- FMEA = inductive (bottom-up); FTA = deductive (top-down from top event, precursor to frequency estimation). FTA models interdependencies of failure modes and produces quantitative system reliability; **FMEA cannot give overall system reliability or design trade-off measures**, nor model a mode whose occurrence raises another mode's probability/severity.
- Selection (7.4): FMEA — comprehensive per-item knowledge, smaller systems, R&D innovation design, many-component series logic; FTA — multiple failure modes, dependencies, redundancy, complex logic; best combined (Chapter 7.4 full mapping). FTA may not get FMEA's detail; some choose FFTA/RBD.

## 7. Report (5.4)
- Must include summary + detailed record + block/functional diagrams + **list of drawings and their issue status**.
- Effects/summary tables (Tables 7–8 pattern): failure modes producing serious effects; recommendations to designers/maintenance/planners/users; design changes already incorporated; effects mitigated by those changes.

## Notes
- 2006 edition has no "interface FMEA" as a named method (2018 3rd edition adds functional FMEA + interface analysis).
- No software-FMEA full procedure — limited postulation/effects (6.3).
- Key doctrine: RPN cautions; high severity should outrank RPN; FMECA insufficient alone for high-risk/complex systems (needs PRA).
